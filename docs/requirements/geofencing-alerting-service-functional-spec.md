# Функциональное техническое задание (BRD / FRD)

**Документ:** `docs/requirements/geofencing-alerting-service-functional-spec.md`
**Статус:** Approved for Development
**Сервис:** geofencing-alerting-service (Поддомен: Telemetry Ingestion & Real-Time IoT)

## 1. Введение и Назначение Сервиса

### 1.1 Бизнес-контекст
Пока `telemetry-ingestion-service` просто принимает гео-точки, `geofencing-alerting-service` непрерывно анализирует этот поток данных в реальном времени. Сервис сравнивает координаты движущихся объектов с гео-зонами (склады, порты, опасные участки) и коридорами допустимых маршрутов, а также отслеживает мгновенные показания датчиков (температура, открытие дверей, удары).

### 1.2 Проблемы, которые решает сервис
*   **Мгновенный детекшн нарушений (Real-time Alerting):** Уведомление диспетчера о срыве температурного режима (например, для фарм-препаратов) или выезде из разрешенного коридора за миллисекунды, а не "постфактум" в конце дня.
*   **Автоматическая фиксация прохождения контрольных точек:** Автоматический отсчет фактов входа и выхода из портов/складов для расчета времени простоя (Demurrage) без участия человека.
*   **Обработка потока событий на лету:** Способность сопоставлять поток 50,000+ гео-точек в секунду с тысячами активных гео-зон с минимальным latency.

## 2. Доменная модель и Сущности (Domain Entities)

Сервис оперирует сущностями потоковой аналитики и пространственной геометрии:

```text
 ┌───────────────────────┐       1..N      ┌─────────────────────────┐
 │     GeofenceZone      ├────────────────►│     GeofenceEvent       │
 └───────────────────────┘                 └─────────────────────────┘
                                                        ▲
 ┌───────────────────────┐                              │ 1..N
 │   TelemetryStream     ├──────────────────────────────┘
 └───────────────────────┘
```

*   **GeofenceZone (Гео-зона / Коридор):** Пространственная сущность. Представляет собой полигон (POLYGON), круг (POINT + радиус) или линейный коридор (LINESTRING + буферная зона в метрах). Атрибуты: `zone_id`, `zone_type` (Warehouse, Port, Restricted_Area, Route_Corridor), `geometry`.
*   **TelemetryStream (Поток телеметрии):** Входящее непрерывное состояние объекта. Атрибуты: `device_id`, `current_location`, `previous_location`, `sensor_data`, `timestamp`.
*   **GeofenceEvent (Гео-событие / Алерт):** Фиксированный бизнес-факт пространственного или физического аномального состояния. Примеры: `GEOFENCE_ENTERED`, `GEOFENCE_EXITED`, `CORRIDOR_DEVIATED`, `TEMPERATURE_EXCEEDED`, `UNAUTHORIZED_DOOR_OPEN`.

## 3. Бизнес-логика и Жизненный Цикл

### 3.1 Состояния пространственного трекинга (State Machine в Kafka Streams)

```text
 [OUTSIDE_ZONE] ──(Координата вошла в полигон)──► [INSIDE_ZONE]
        ▲                                                │
        │                                                │ (Сработка датчика)
        │ (Координата вышла из полигона)                  ▼
        └───────────────────────────────────────── [ZONE_ALERT]
```

### 3.2 Основные бизнес-сценарии (Use Cases)

**UC-1: Детекция входа/выхода из гео-зон (Entry/Exit Detection)**
1.  Поступает точка с координатами объекта $T_n$.
2.  Сервис сопоставляет $T_n$ и предыдущую точку $T_{n-1}$ с базой активных гео-зон объекта.
3.  Если $T_{n-1}$ была снаружи, а $T_n$ внутри полигона — генерируется событие `GEOFENCE_ENTERED`.
4.  Если $T_{n-1}$ была внутри, а $T_n$ снаружи — генерируется событие `GEOFENCE_EXITED`.

**UC-2: Контроль соблюдения коридора маршрута (Route Corridor Drift)**
1.  Для активного рейса задана допустимая линия пути и буферная зона (например, 500 метров в обе стороны).
2.  При поступлении точки сервис высчитывает кратчайшее расстояние от точки до линии LINESTRING маршрута.
3.  Если отклонение превышает 500 метров в течение $N$ точек подряд — генерируется критический алерт `CORRIDOR_DEVIATED`.

**UC-3: Мониторинг температурных и физических аномалий (Threshold Alerts)**
1.  Сервис считывает карту показаний датчиков из телеметрии (`sensors_map`).
2.  Проверяются лимиты (например, $-20^\circ\text{C} \le T \le -18^\circ\text{C}$).
3.  Если температура поднялась до $-15^\circ\text{C}$ и держится более 3 минут, срабатывает правила алертинга `TEMPERATURE_EXCEEDED` с отправкой экстренного push-уведомления водителю и диспетчеру.

## 4. Функциональные требования (Functional Requirements)

*   **FR-1:** Сервис ДОЛЖЕН непрерывно потреблять нормализованный поток телеметрии из Kafka.
*   **FR-2:** Сервис ДОЛЖЕН поддерживать кеширование и пространственное индексирование гео-зон в оперативной памяти за $O(1)$ / $O(\log N)$.
*   **FR-3:** Сервис ДОЛЖЕН фиксировать события входа, выхода и пребывания объекта внутри гео-зон.
*   **FR-4:** Сервис ДОЛЖЕН детектировать факты отклонения от траектории маршрута (Corridor Drift).
*   **FR-5:** Сервис ДОЛЖЕН оценивать состояние датчиков (температура, открывание дверей, удары) и генерировать алерты при выходе за пороговые значения.
*   **FR-6:** Сервис ДОЛЖЕН транслировать сгенерированные события и алерты в выходные топики Kafka в формате Avro.

## 5. Требования к качеству и SLA (Non-Functional Requirements)

*   **NFR-1 (Real-Time Processing):** Задержка обработки гео-точки и генерации алерта — не более 50 ms (p99) с момента поступления в Kafka.
*   **NFR-2 (Scalability):** Способность горизонтально масштабироваться путем увеличения партиций Kafka и инстансов сервиса (Stateful Stream Processing).
*   **NFR-3 (Accuracy):** Исключение ложных алертов "дребезга" на границе гео-зон (использование алгоритмов Hysteresis / Debouncing).
